Why this exists

What is LangGraph — and why a graph?

LangGraph lets you wire small Python functions into a graph that runs them in order, passing a shared state from one step to the next.

  • A plain script runs top to bottom. To branch or loop you hand-write if and while tangles that get messy fast.
  • A graph makes the flow explicit data: nodes do work, edges decide what runs next — including branches and waiting for a human.
Key idea You describe what runs and what runs next. LangGraph handles passing state through, branching, and pausing — so the control flow is something you can see, not bury in code.

The whole course in one picture

Three building blocks: State · Nodes · Edges

State

The shared data that travels through every step.

Nodes

Functions that read state and return updates.

Edges

Connections that decide what runs next.

Building block 1

State

from typing import Optional
from typing_extensions import TypedDict

class GraphState(TypedDict):
    question: Optional[str]
    classification: Optional[str]
    response: Optional[str]

What this does: declares the typed shape of the data that travels between nodes.

State is a shared dictionary (a TypedDict) that flows through the whole graph.

  • Every node receives the current state.
  • Every node returns a partial dict that LangGraph merges back in.

Building block 2

Nodes

def classify_input_node(state: GraphState) -> dict:
    question = (state.get("question") or "").strip()
    return {"classification": classify(question)}

What this does: a node reads one field from state and returns the field it computed.

A node is just a plain Python function. It does one step of work.

  • Takes the state as input.
  • Returns a partial dict of updates — not the whole state.

Building block 3

Edges — including conditional

workflow.add_edge(START, "classify_input")
workflow.add_conditional_edges(
    "classify_input",
    decide_next_node,
    {"handle_greeting": "handle_greeting",
     "handle_search": "handle_search"},
)

What this does: wires the entry edge, then branches to one of two nodes based on the router's return value.

A plain edge always goes A → B. A conditional edge runs a router function whose return value (mapped to a node name) picks the branch.

Putting it together

The lifecycle: build → compile → invoke

app = workflow.compile()
result = app.invoke({"question": "Hi, how are you?"})
print(result)

What this does: compiles the graph definition into a runnable object and executes it with an initial state.

Key idea The graph is just data until you compile it. invoke() then runs it from START to END.

Example 1 · teaches Conditional Edges

simple_graph.py

A tiny graph that classifies a question and routes it to the right handler.

Two kinds of node, side by side: handle_greeting is a plain canned reply, while handle_search calls an LLM via OpenRouter — proof that an LLM node is just a node.

Why it matters Conditional edges: a router function reads state and picks which node runs next.

Example 1 · the flow

How it runs

  • 1. Define state — holds question, classification, response.
  • 2. Classify — START flows into classify_input, tagging the question as greeting or search.
  • 3. Route — the router reads classification and returns the next node's name.
  • 4. Handle — handle_greeting (canned) or handle_search (calls OpenRouter) runs and sets response.
  • 5. Finish — both branches go to END; invoke returns the merged state.

Example 1 · the code

The node, the router, the wiring

def classify_input_node(state: GraphState) -> dict:
    question = (state.get("question") or "").strip()
    return {"classification": classify(question)}

def decide_next_node(state: GraphState) -> str:
    return "handle_greeting" if \
        state.get("classification") == "greeting" \
        else "handle_search"

What this does: the node tags the question; the router returns the name of the next node to run based on that tag.

workflow.add_edge(START, "classify_input")
workflow.add_conditional_edges(
    "classify_input",
    decide_next_node,
    {"handle_greeting": "handle_greeting",
     "handle_search": "handle_search"},
)
workflow.add_edge("handle_greeting", END)
workflow.add_edge("handle_search", END)

What this does: START enters classify_input, the router picks a branch, and both branches end at END.

Example 1 · run it

Compile, invoke, and the real output

app = workflow.compile()
# greeting branch (plain node)
print(app.invoke({"question": "Hi, how are you?"}))
# search branch (LLM via OpenRouter)
print(app.invoke({"question": "What is LangGraph?"}))

What this does: compiles the graph, then runs it twice — each input takes a different branch.

# $ python simple_graph.py
{'question': 'Hi, how are you?',
 'classification': 'greeting',
 'response': 'Hello! How can I help you today?'}

{'question': 'What is LangGraph?',
 'classification': 'search',
 'response': 'LangGraph is a framework for building '
             'stateful, multi-step LLM apps as graphs.'}

What this does: two merged states — greeting ran the plain node; search ran the LLM node and filled response from OpenRouter.

Example 2 · teaches How State Transfers

state_flow_demo.py — Watch state move

An interactive console tool (no UI, no API key) whose only job is to make the invisible visible: it prints every IN → OUT → MERGE as data moves between nodes.

  • IN — the full state handed into a node.
  • OUT — the partial dict the node returned.
  • MERGE — the state after LangGraph merges that partial back in.

Type a message and press Enter to step the graph one node at a time (STEP mode); :auto runs straight through, :stream shows LangGraph's native view.

Key idea A node never returns the whole state — just the keys it changed. LangGraph merges that partial back in for the next node.

Example 2 · the topology

ingest → analyze → route → finalize

After analyze, the router returns one of faq / smalltalk / else — the three branches all converge on finalize, then END.

Example 2 · the code

A partial-returning node + the router

def analyze(state: ChatState) -> dict:
    tokens = state.get("tokens") or []
    category = categorize(tokens)   # faq / smalltalk / other
    return {
        "category": category,
        "sentiment": judge(tokens),
        "steps": state["steps"] + ["analyze"],
    }

What this does: reads tokens, returns only the keys it changed. steps is rebuilt by hand (old list + new name) because a plain TypedDict replaces lists on merge.

def route_by_category(state: ChatState) -> str:
    cat = state.get("category")
    return {"faq": "handle_faq",
            "smalltalk": "handle_smalltalk"
           }.get(cat, "escalate")

workflow.add_conditional_edges(
    "analyze", route_by_category,
    {"handle_faq": "handle_faq",
     "handle_smalltalk": "handle_smalltalk",
     "escalate": "escalate"})

What this does: the router reads category and returns the next node's name; the mapping turns that string into the branch LangGraph jumps to.

Example 2 · see the transfer

The console trace

# type: "please cancel my invoice"
EDGE: START  ──>  ingest
  IN    state   = {text='please cancel my invoice', steps=[]}
  OUT   partial = {tokens=[...], steps=['ingest']}
  MERGE state   = {... steps=['ingest']}

EDGE: ingest  ──>  analyze
  IN    state   = {... steps=['ingest']}
  OUT   partial = {category='faq', steps=['ingest','analyze']}
ROUTER route_by_category: category='faq' => 'handle_faq'

What this does: each block is one node — you literally read the state go IN, the partial come OUT, and the MERGE result handed to the next edge.

EDGE: handle_faq  ──>  finalize
  OUT   partial = {status='done',
                   steps=[...,'finalize']}

PATH TAKEN:
  START -> ingest -> analyze
        -> handle_faq -> finalize -> END

FINAL STATE:
  category = 'faq'
  status   = 'done'
  steps    = ['ingest','analyze',
              'handle_faq','finalize']

What this does: the steps list accumulates every node that ran — proof that state carried data the whole way through and merged at each hop.

Example 3 · teaches Persistence & Threads

memory_demo.py — Memory that remembers

A deterministic "memory bot" (no LLM, no API key). One node answers, but a checkpointer saves the state after every run — keyed by thread_id.

  • Same thread_id → the saved state is loaded and memory keeps growing.
  • Different thread_id → a fresh, separate, empty memory.
Key idea The thread_id is the key your conversation is saved under. Reuse it to resume; change it to start over.

Example 3 · the code

The checkpointer and the thread_id

from langgraph.checkpoint.memory import InMemorySaver

app = builder.compile(
    checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "alice"}}
app.invoke({"user_message": msg}, config=config)

What this does: the checkpointer persists state after each invoke; thread_id is the key it saves under. Same id loads that saved state before the node runs.

import operator
from typing import Annotated

class MemState(TypedDict):
    user_message: str
    history: Annotated[list, operator.add]
    turn: Annotated[int, operator.add]

What this does: the reducer Annotated[list, operator.add] makes history append on merge — the node returns just the new turn and LangGraph grows the list automatically.

Example 3 · memory grows

Before & after, across turns

[alice] BEFORE -> remembered 1 turn(s)
[alice] turn counter now: 2
[alice] BEFORE -> remembered 2 turn(s)

What this does: alice's memory grows 1 → 2 → 3 on the same thread, while bob starts empty on his own thread.

# back to "alice" — memory RESUMES
[alice] BEFORE -> remembered 3 turn(s)

        previously said: [...]
[alice] turn counter now: 4

# two independent saved memories
alice : 4 turns
bob   : 1 turn

What this does: switching back to "alice" resumes at turn 4 — proof the checkpointer kept her state keyed by thread_id, separate from bob's.

See it live

LangGraph Studio

The local dev server and visual UI for LangGraph. It discovers your compiled graph and renders it so you can watch it execute node-by-node — no API key needed for the demo graph.

# launch the local dev server
$ cd studio && ../.venv/bin/langgraph dev

What this does: starts the dev server, which reads langgraph.json and opens the visual graph UI. (Already running at http://127.0.0.1:2024.)

# langgraph.json
{
  "dependencies": ["."],
  "graphs": {
    "agent": "./agent.py:graph"
  },
  "env": ".env"
}

What this does: points the dev server at the module-level compiled graph named graph in agent.py.

  • Graph topology drawn as a diagram you can read at a glance.
  • Node-by-node run with execution highlighting so you follow the path through the branch.
  • State inspector on the right: fields fill in as each node runs.
  • Editable input panel to change the message and re-run.
  • Threads / time-travel persistence the dev server provides automatically.
Heads up The Chat tab is greyed out because this graph's state uses plain string fields. Drive it from the Input panel instead, and read the finalize node's final field for the answer.

classify → branch → finalize

Same shape as Example 1, one branch wider: classify routes to one of four handlers, all converging on finalize → END.

Studio · how information flows

The inspector IS the IN/OUT/MERGE

What you watched scroll past in Example 2's console is exactly what Studio shows you visually, node-by-node, as the run progresses:

  • The highlighted node is the one receiving state IN.
  • The state inspector updating is the partial coming OUT and being MERGED back in.
  • The lit-up edge is the transfer to the next node.
Maps to Example 3 Studio's Threads are thread_ids, and time-travel is the checkpointer's saved snapshots — the same persistence from memory_demo.py, made clickable. 
# classify emits a partial...
classify  ──>  {intent: "complaint",
               sentiment: "negative"}
# ...finalize reads merged state
finalize  ──>  {final: "[intent=complaint | ...]"}

What this does: read the finalize node's final field in the inspector — it's the converged result after every merge.

Observability & evals

LangSmith — see inside the black box

An observability + evaluation platform for LLM apps, from the LangChain team. It works with or without LangChain / LangGraph.

  • LLM apps are non-deterministic black boxes — the same input can give different answers.
  • You can't debug them by reading logs — the interesting part is what the model saw and said.
  • LangSmith records exactly what went in and out at every step of every run.
Key idea Studio shows you one run, live. LangSmith keeps every run — to debug, test, and watch in production.

The signature feature

A trace is a tree of runs

One run of your app, captured as nested runs (spans) — the graph run, each node, each LLM call — each with inputs, outputs, latency, tokens, cost, and errors.

Read it like a flame chart Indentation = nesting; bar length = time. The long respond → LLM call bar is instantly where the run spent its time.

Zero code change

Turn it on with three env vars

# .env — no code change needed
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_...
LANGSMITH_PROJECT=my-project   # optional

What this does: any LangGraph / LangChain app auto-traces once these are set — no SDK calls to add. (Older aliases still work: LANGCHAIN_TRACING_V2, LANGCHAIN_API_KEY.)

Tie it back Run our langgraph dev with LANGSMITH_API_KEY set, and every run shows up as a trace — nothing else to wire up.

Debug in seconds, not hours

What a trace shows you

  • Inputs & outputs at every step — the exact prompt sent and text returned.
  • Latency per run — find the slow node at a glance.
  • Tokens & estimated cost — per call and rolled up.
  • Errors — the failing step is marked in red.
The payoff When an answer is wrong, you jump straight to the step that broke and read what it actually saw — no print() archaeology.

From runs to test cases

Projects, Datasets & Examples

  • Projects group traces — e.g. one per app or environment.
  • Datasets hold Examples: saved input → expected output pairs.
  • Capture examples straight from real traces (one click) or write them by hand.
  • A dataset is your app's suite of test cases — the thing you evaluate against.
The move See a run that's a good (or bad) example? Add it to a dataset. Your test set grows from real usage.

Grade your app at scale

Evaluations: dataset → run → score

Run your app over every example in a dataset, then score each output with an evaluator. Regression-test your prompts and graph like real code.

Code / heuristic evaluators

Deterministic checks: exact match, contains, valid-JSON, regex, length. Fast and free.

LLM-as-a-judge

A strong model grades the output against criteria — for when there's no single exact answer.

When there's no exact right answer

LLM-as-a-judge

Use a strong LLM to grade outputs against criteria — correctness, relevance, helpfulness, groundedness.

  • Scoring: the judge reads the output (and any reference) and returns a score + reason.
  • Pairwise: show it two answers and ask which is better — great for comparing prompt versions.
Caveats Judges can be biased or inconsistent. Calibrate against a few human labels, keep the judge prompt specific, and don't treat its score as ground truth.

Once it's live

Feedback & monitoring in production

  • Feedback = scores attached to runs — a human thumbs-up / down, or an automated evaluator running on live traffic.
  • Monitoring dashboards track latency, cost, error rate, and feedback over time.
  • Spot a regression the day it ships — a spike in errors or a drop in thumbs-up stands out on the chart.
Same data, two uses A trace helps you debug one run; the dashboards help you watch all of them in aggregate.

Ship it

You built an agent — now how do others use it?

So far the graph runs on your machine. To let a teammate (or a room full of people) use it, it needs to be reachable.

  • The real question: what's the simplest way to deploy — for free?
  • Good news: for a live demo you're one flag away; for a permanent public app, one small wrapper away.
Where we're headed Four tiers, from local-only to managed cloud. The first three are free — we'll spend our time there.

The landscape

The deploy spectrum: Tier 0 → 3

Left to right = more reach, more setup. Tiers 0–2 cost nothing; Tier 3 is the paid, production option.

Tier 1 · the simplest free deploy

langgraph dev --tunnel

# same dev server, now public
$ ../.venv/bin/langgraph dev --tunnel

# prints a public tunnel URL, e.g.
# https://<random>.tunnel...  ← share this

What this does: runs the exact same dev server, but the --tunnel flag exposes it at a public URL anyone can reach — even Studio works remotely against it.

  • No account, no key, no cost.
  • One command — great to share a live agent or when a network blocks localhost.
One-liner Want to put a live agent in front of the room, free? langgraph dev --tunnel and share the URL.

Tier 2 · permanent & free

Wrap the graph in a small app

# tiny web app around the compiled graph
import streamlit as st
from agent import graph   # compiled LangGraph

msg = st.chat_input("Ask the agent…")
if msg:
    out = graph.invoke({"question": msg})
    st.write(out["response"])

What this does: a few lines of UI call graph.invoke(...) — the same graph you already built — then deploy that app to a free host for a permanent, always-on URL.

Free tiers to name: Hugging Face Spaces, Streamlit Community Cloud, Render free web service.

Tier 3 · the paid landscape

What's paid: LangGraph Platform

  • LangGraph Platform — a one-click cloud deploy straight from the LangSmith UI, with autoscaling, persistence, and a managed API.
  • Self-hosting the LangGraph API server (langgraph build / langgraph up) needs a LANGSMITH_API_KEY with deployment access, or a LANGGRAPH_CLOUD_LICENSE_KEY.
  • This is the production path — and it is not the free path.
Be clear with yourself For learning and demos, stay on Tiers 0–2 (free). Reach for the Platform when you need real uptime, scale, and a managed API — and are ready to pay for it.
